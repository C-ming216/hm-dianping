## 一、功能全景与数据流

发笔记 = 用户登录后，选一张探店图片 + 选一家商户 + 填标题和内容，发布成一条博客记录。

```
blog-edit.html (Vue2)
   │
   ├─① checkLogin()      → GET  /user/me                 校验登录态
   ├─② queryShops()      → GET  /shop/of/name?name=      模糊搜索商户
   ├─③ fileSelected()    → POST /upload/blog             上传图片（FormData）
   ├─④ deletePic()       → GET  /upload/blog/delete      删除已传图片
   └─⑤ submitBlog()      → POST /blog                    发布笔记（最终入库）
                                    │
                                    ▼
                          tb_blog 表 INSERT 一条记录
```

nginx 在中间的角色：前端请求都带 `/api` 前缀，nginx 去掉前缀转发给 8081；上传的图片文件必须落在 nginx 静态目录下才能被浏览器显示（本功能最大的坑，见第四节）。

## 二、接口契约（从 blog-edit.html 反推）

| # | 前端调用 | Method | 入参 | 前端期望的返回 | 后端现状 |
|---|---------|--------|------|---------------|---------|
| ① | `/user/me` | GET | 无（header 带 token） | 用户信息，失败则跳 login.html | ✅ 已实现 |
| ② | `/shop/of/name?name=` | GET | 商户名关键字 | 商户数组（取 `id`、`name`） | ✅ 已实现（ShopController:92） |
| ③ | `/upload/blog` | POST | `multipart/form-data`，字段名 `file` | 文件名字符串（前端拼 `/imgs` 前缀展示） | ⚠️ 已实现但**保存路径有坑** |
| ④ | `/upload/blog/delete?name=` | GET | 图片文件名 | 只关心 success | ✅ 已实现 |
| ⑤ | `/blog` | POST | JSON：`{title, content, images, shopId}` | 返回新笔记 id | ✅ 基础版已实现，**结构待重整** |

`submitBlog()`（blog-edit.html 108~115 行）拼请求体的逻辑：

```js
let {...data} = this.params;              // title、content
data.images = this.fileList.join(",");    // 图片名数组 → 逗号分隔字符串
data.shopId = this.selectedShop.id;       // 选中商户 id
axios.post("/blog", data)
```

对照 `Blog` 实体：`title / content / images / shopId` 是真实列；`userId` 不传由后端取；`icon / name / isLike` 是 `@TableField(exist = false)` 辅助字段。

## 四、核心坑：IMAGE_UPLOAD_DIR 指向不存在的 D 盘

`SystemConstants.java` 第 4 行：

```java
public static final String IMAGE_UPLOAD_DIR = "D:\\lesson\\nginx-1.18.0\\html\\hmdp\\imgs\\";
```

问题链条：上传的文件被写到 **D 盘** → 前端拿文件名拼 `/imgs/...` 让 **nginx（从 E 盘 `html/hmdp` 提供静态服务）** 去读 → D 盘写的、E 盘找 → **图片全部裂图**。

> 学习点：文件上传的"保存位置"必须和"静态资源服务位置"是同一个地方。企业里一般用 OSS/MinIO 对象存储，存和读天然在同一个服务。

### 9.1 `SystemConstants`（修改，1 行）

- **职责**：存放全局常量（上传目录、分页大小）
- **现有属性**：
  - `IMAGE_UPLOAD_DIR`（第 4 行）❌ 要改
  - `MAX_PAGE_SIZE = 10`（不动）
- **修改点**：

```java
// 改前（课程老师 D 盘路径，你机器上不存在有效前端）
public static final String IMAGE_UPLOAD_DIR = "D:\\lesson\\nginx-1.18.0\\html\\hmdp\\imgs\\";
// 改后（指向你 E 盘真实前端目录，与 nginx 静态服务根目录对齐）
public static final String IMAGE_UPLOAD_DIR = "E:\\JAVA\\Project\\web-front-hm-dianping\\nginx-1.18.0\\html\\hmdp\\imgs\\";
```

- **验证方法**：重启后端传一张图，确认文件出现在 `E:\...\imgs\blogs\{d1}\{d2}\` 下且页面回显正常
- **被谁依赖**：`UploadController.uploadImage()`（写文件）和 `deleteBlogImg()`（删文件）都读这个常量——改一处全生效，这就是常量收敛的价值

### 9.2 `IBlogService`（修改接口签名）

- **职责**：Blog 业务服务的抽象契约
- **现有方法**：`void saveBlog(Blog blog);` —— **问题：返回 void，Controller 拿不到新笔记 id**
- **改为**：

```java
Long saveBlog(Blog blog);   // 返回新笔记主键 id，供 Controller 包装给前端
```

- **设计要点**：
  - 入参只传 `Blog`：userId 在 Service 内部从 `UserHolder` 取（取登录态属于业务语义，放 Service 更纯粹；**本方案放 Service**，与现有 `BlogServiceImpl` 风格一致）
  - 返回 `Long` 而不是 `Blog`：前端只消费 id，最小暴露原则

### 9.3 `BlogServiceImpl`（修改，核心业务逻辑）

- **职责**：发笔记的业务规则实现（校验 + 补全 + 入库）
- **类声明**（不动）：`extends ServiceImpl<BlogMapper, Blog> implements IBlogService`——继承 MyBatis-Plus 的 `IService`，天然拥有 `save()` 方法
- **重写 `saveBlog`，核心逻辑按顺序 5 步**：

```
① 取登录用户   UserDTO user = UserHolder.getUser();
              user == null → 返回 null（拦截器理论上已挡，防御性判空）
② 参数校验     blog.getTitle() 为空、blog.getShopId() == null → 返回 null
              （Service 不返回 Result——保持无 HTTP 语义；null 交由 Controller 翻译成 fail）
③ 图片数量校验  blog.getImages() 非空时，split(",").length > 9 → 返回 null
④ 补全字段     blog.setUserId(user.getId())
⑤ 入库并返回   save(blog); return blog.getId();
              （MyBatis-Plus 对 null 字段默认不拼 INSERT，liked/comments 靠表默认值 0）
```

- **要不要加 `@Transactional`？** 单表单条 INSERT，**不需要**。判断标准：方法里有**多个写操作且要求同成败**才需要事务。将来 Feed 流版会加"入库 + 推送粉丝收件箱"，届时若推送失败不能回滚入库（推送是尽力而为），依然不加——这是值得记住的设计权衡
- **加分项（自己决定加不加）**：调 `IShopService.getById(shopId)` 校验商户存在性。要想清楚：多一次 DB 查询换数据一致性，值不值？

### 9.4 `BlogController`（修改，瘦身为薄壳）

- **职责**：接收 HTTP 请求 → 调 Service → 把结果包装成 `Result` 返回。**不写业务逻辑**
- **改后 `saveBlog` 的全部逻辑就 3 步**：

```
① Long id = blogService.saveBlog(blog);
② id == null → return Result.fail("参数不合法或未登录");
③ return Result.ok(id);
```

- **改前的反面对照**（现在 Controller 里那段）：取 UserHolder、setUserId、save 全在 Controller——等于 Service 层白建了，而且和 `BlogServiceImpl.saveBlog` 死代码重复。改造后 Controller 不再 import `UserHolder`，这是检验"瘦没瘦"的直观标志
- **类上已有注解**（不动）：`@RestController` + `@RequestMapping("/blog")`

### 9.5 无需修改但必须看懂的 4 个类（调用链上下游）

| 类 | 在链路中的角色 | 关键点 |
|----|--------------|--------|
| `Blog`（entity） | `@RequestBody` 反序列化的目标 + ORM 映射 | `icon/name/isLike` 是 `@TableField(exist=false)`，不进数据库 |
| `LoginInterceptor` + `UserHolder` | 请求进来先过拦截器，解析 JWT → 存 `ThreadLocal` → Controller/Service 用 `UserHolder.getUser()` 取 | **为什么不能用前端传 userId**：可伪造；ThreadLocal 绑定当前线程，天然防串号 |
| `UploadController` | 图片上传/删除，已完整，不动 | 依赖 9.1 的常量，路径修好后自动正确 |
| `MvConfig` | 拦截器注册 + 放行白名单 | `/blog`、`/upload/**` 不在放行列表 = 必须登录，正确，**别手贱加进白名单** |

### 9.6 调用关系图（改造后）

```
HTTP POST /api/blog (带 token)
        │ nginx 去掉 /api 前缀转发 8081
        ▼
LoginInterceptor ──解析 JWT──► UserHolder (ThreadLocal 存 UserDTO)
        │ 放行（已登录）
        ▼
BlogController.saveBlog(@RequestBody Blog)     ← 只做协议转换
        │ blogService.saveBlog(blog)
        ▼
IBlogService (接口) ──实现──► BlogServiceImpl.saveBlog()
        │ ①UserHolder.getUser() ②校验 ③补全 ④save()
        ▼
ServiceImpl.save() ──MyBatis-Plus──► BlogMapper ──► tb_blog (INSERT)
        │ 回填自增 id
        ▼
BlogController: Result.ok(blog.getId()) ──► 前端跳转 info.html
```

**依赖方向**：Controller → Service 接口 → ServiceImpl → Mapper → DB。Controller 只依赖 `IBlogService` 接口（面向接口编程），从不直接碰 Mapper。

## 八、常见坑清单

1. **图片裂图** = 上传保存目录 ≠ nginx 静态目录（§4 核心坑）
2. **401/跳登录** = 请求没带 token 或 Access Token 过期（30 分钟短）
3. **`/blog` 返回 404** = 没编译新代码，先 `mvn clean compile` 再重启
4. **图片上传 500** = 目标磁盘路径不可写，看控制台 `IOException`
5. **改了接口签名编译报错** = `IBlogService`、`BlogServiceImpl`、`BlogController` 三处要同步改，漏一处就红
6. **发布成功但列表没有** = `user_id` 没写入（UserHolder 取的是 UserDTO 不是 User）
